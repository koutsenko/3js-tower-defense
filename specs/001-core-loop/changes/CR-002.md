# Change Request: CR-002 — Терминология временных операций gameplay

**Feature:** `001-core-loop`  
**Status:** Approved  
**Дата:** 2026-08-29  
**Источник:** code review реализации `001-core-loop`

## Решение после утверждения

CR-002 утверждён пользователем 2026-08-29. Изменения `spec.md` не требуются.
Разрешено синхронизировать `plan.md`, добавить `T-018` в `tasks.md` и после
этого выполнить переименования отдельным implementation change с сохранением
существующего gameplay behavior.

## 1. Причина изменения

В ходе code review обнаружено, что gameplay-функции с префиксом `getNext`
выполняют разные по смыслу операции:

- читают установленное расписание;
- детерминированно вычисляют следующую временную отметку;
- условно прогнозируют будущее событие из текущего состояния;
- предоставляют вспомогательное значение для последующей проверки фактического
  состояния на достигнутой simulation boundary.

Например, `getNextSpawnTime` вычисляет точный момент из неизменного spawn
schedule, а `getNextEscapeTime` прогнозирует выход monster при условии, что он
продолжит движение и не будет уничтожен раньше. Общее `getNext` скрывает это
различие и затрудняет чтение boundary loop.

Отдельно `getNextRangeEntryProgress` воспринимается как текущая targeting
операция, хотя функция прогнозирует место возможного будущего входа monster в
tower range. Фактическая доступность цели проверяется позднее через `isInRange`
после перехода runtime к рассчитанной boundary.

Цель изменения — утвердить единую naming methodology для temporal operations и
применить её к существующему gameplay-коду без изменения игровых правил,
порядка systems, timing или authoritative state.

## 2. Scope и non-goals

В scope входят:

- соглашение о префиксах temporal и boundary operations;
- переименование существующих gameplay-функций в соответствии с их ролью;
- уточнение имён predicates и selectors, участвующих в targeting;
- обновление imports, tests и identifier-frequency report;
- regression verification неизменности runtime behavior.

В scope не входят:

- изменение `FR` или `AC`;
- изменение fixed-step application cadence;
- изменение interval splitting или system order;
- добавление сохранённого event calendar либо долгоживущих prediction objects;
- изменение gameplay balance;
- системное переименование документированного поля `routeProgress`;
- реорганизация gameplay-файлов и введение `predictions.ts`, `Route` или
  `RouteSegment`;
- актуализация устаревшего `AGENTS.md`, которая должна выполняться отдельным
  repository documentation change.

## 3. Предлагаемая naming methodology

Имена gameplay-функций должны отражать не только возвращаемое значение, но и
роль операции в обработке simulation boundaries.

- `get` — чтение уже существующего значения состояния без прогнозирования,
  существенного вычисления или мутации;
- `calculate` — детерминированное вычисление значения из расписания,
  конфигурации или переданных аргументов;
- `predict` — условное вычисление будущего gameplay event или boundary из
  текущего состояния; результат может потерять актуальность после другого
  события и вычисляется заново;
- `is`, `has`, `can` — проверка фактического состояния на текущей simulation
  boundary;
- `select` — выбор сущности из фактически доступных кандидатов;
- `schedule` — сохранение будущего события или времени для последующего
  использования;
- `resolve` — применение уже наступившего события и связанных изменений
  authoritative state;
- `advance`, `move` — продвижение состояния на переданный интервал времени.

`predict` не означает вероятностный результат. Prediction является точным при
текущем state и config, но условным относительно последующих gameplay events.
После обработки ближайшей boundary старые predictions отбрасываются, а новые
вычисляются из обновлённого state.

## 4. Предлагаемые переименования

Ни одно из перечисленных имён функций буквально не зафиксировано в `spec.md`
или `plan.md`; документы описывают соответствующее поведение.

| Старое имя | Новое имя | Что функция делает | Упомянута ли в spec или plan |
|---|---|---|---|
| `getNextRangeEntryProgress` | `predictNextTowerRangeEntry` | Прогнозирует ближайший вход конкретного monster в range конкретной tower | Точного имени нет; поведение связано с `FR-007` и targeting design |
| `getNextTargetingTime` | `predictNextTargetingBoundaryTime` | Прогнозирует следующую boundary для повторной проверки target availability или tower readiness | Точного имени нет; поведение связано с `FR-007`, `FR-011` и interval processing |
| `getNextEscapeTime` | `predictNextMonsterEscapeTime` | Прогнозирует ближайший escape живого monster при сохранении текущего движения | Точного имени нет; поведение связано с `FR-006`, `FR-010` и boundary processing |
| `getNextProjectileImpactTime` | `predictNextProjectileImpactTime` | Прогнозирует ближайшее попадание активного projectile в назначенный target | Точного имени нет; поведение связано с `FR-008` и projectile design |
| `getNextSpawnTime` | `calculateNextSpawnTime` | Вычисляет следующий момент установленного spawn schedule | Точного имени нет; расписание задано в `FR-006` |
| `getNextProjectileStepTime` | `calculateNextProjectileStepTime` | Вычисляет следующую отметку fixed projectile step | Точного имени нет; fixed-step processing описан в `plan.md` |
| `isInRange` | `isMonsterInTowerRange` | Проверяет фактическое положение monster относительно tower range на текущей boundary | Точного имени нет; правило задано в `FR-007` |
| `selectTarget` | `selectTowerTarget` | Выбирает фактический target конкретной tower среди доступных сейчас monsters | Точного имени нет; алгоритм выбора задан в `FR-007` |

Следующие имена сохраняются, поскольку уже соответствуют утверждаемой
методике:

- `scheduleProjectileImpact`;
- `spawnDueMonsters`;
- `resolveEscapedMonsters`;
- `resolveProjectileHits`;
- `resolveDefeat`;
- `resolveVictory`;
- `fireReadyTowers`;
- `advanceWave`;
- `moveMonsters`;
- `moveProjectiles`;
- `getNextEntityId`, поскольку эта функция не прогнозирует gameplay event.

## 5. Контракт prediction operations

Prediction operations:

1. не изменяют authoritative state;
2. вычисляются только из current state, config и явно переданных аргументов;
3. возвращают ближайшую подходящую boundary, место события либо `null`;
4. не гарантируют, что спрогнозированная entity сохранится до boundary;
5. не заменяют фактические predicates, selectors и resolvers;
6. после обработки другой boundary вычисляются заново.

Для targeting сохраняется следующий смысловой поток:

```text
predictNextTowerRangeEntry
        ↓
predictNextTargetingBoundaryTime
        ↓
advance to boundary
        ↓
isMonsterInTowerRange
        ↓
selectTowerTarget
        ↓
fireReadyTowers
```

`predictNextTowerRangeEntry` предлагается возвращать предметный результат, а не
неименованный scalar:

```ts
interface TowerRangeEntryPrediction {
  readonly routeProgress: number;
}
```

Поле временно сохраняет утверждённый термин `routeProgress`. Его возможная
замена на явно измеряемое расстояние должна рассматриваться отдельно, поскольку
`routeProgress` используется в `spec.md`, `plan.md`, state model и tests.

## 6. Влияние на `spec.md`

Изменения `spec.md` не предлагаются. CR не меняет player-visible behavior,
functional requirements или acceptance criteria.

После переименования должны сохраниться:

- partition invariance `FR-006`;
- targeting range, target selection и cooldown `FR-007`;
- projectile tracking и damage `FR-008`;
- escape semantics `FR-010`;
- строительство и немедленное участие новой tower `FR-011`;
- terminal ordering `FR-013`.

## 7. Предлагаемые изменения `plan.md`

После утверждения CR добавить раздел `Naming of temporal operations` в раздел
модулей и dependency direction либо рядом с interval-processing design.

Раздел должен:

- утвердить методику из раздела 3 настоящего CR;
- объяснить отличие application tick от внутренних gameplay boundaries;
- зафиксировать, что predictions являются эфемерными и пересчитываются после
  каждой обработанной boundary;
- привести примеры `calculateNextSpawnTime`,
  `predictNextTargetingBoundaryTime`, `isMonsterInTowerRange` и
  `resolveProjectileHits`;
- не фиксировать лишние детали размещения приватных helpers по файлам.
