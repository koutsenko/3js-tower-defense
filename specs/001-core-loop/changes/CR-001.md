# Change Request: CR-001 — Семантика времени на lifecycle и spawn boundaries

**Feature:** `001-core-loop`  
**Status:** Approved
**Дата:** 2026-08-25  
**Источник:** review реализации `T-006`

## Решение после утверждения

После утверждения impact analysis принято решение переоткрыть `T-005` со
статусом `Pending` для реализации и regression verification обновлённой runtime
boundary. Это последующее решение заменяет первоначальную рекомендацию раздела
6.1 сохранить для `T-005` статус `Complete`. `T-006` переведена из `Blocked` в
`Pending`, но остаётся зависимой от повторного завершения `T-005`.

## 1. Причина изменения

Утверждённые требования задают 20-секундную подготовку, spawn monsters по
расписанию `0/2/…/18` секунд и скорость движения `1 cell/s`. Утверждённый
technical design одновременно предоставляет публичный метод
`advance(deltaSeconds)` и описывает выполнение gameplay систем fixed steps по
`1/60 s`.

При реализации `T-006` обнаружено, что документы не определяют, как runtime
должен обрабатывать один вызов `advance(deltaSeconds)`, пересекающий границу
начала волны или одну либо несколько границ spawn schedule. Без такого правила
невозможно однозначно определить active time нового monster и гарантировать
одинаковый результат при разном разбиении одного gameplay interval.

Изменение не должно корректировать balance, маршрут, размер волны или
player-visible длительности. Его цель — формализовать уже ожидаемые timing rules
как однозначный и тестируемый runtime contract.

## 2. Обнаруженное противоречие

Текущий tick order в `plan.md` требует:

1. продвинуть lifecycle;
2. создать всех monsters, срок spawn которых наступил;
3. переместить живых monsters на величину текущего шага.

При этом не определено, относится ли полный `deltaSeconds` к monster, который
появился внутри этого же интервала. Наивная реализация сначала создаёт всех due
monsters, а затем двигает каждого на `MONSTER_SPEED × deltaSeconds`. В результате
monster получает движение за время до своего scheduled spawn.

Пример для одного вызова, продвигающего волну от `0 s` до `4 s`:

| `spawnIndex` | Scheduled spawn | Ожидаемый active time | Ошибочный active time |
|---:|---:|---:|---:|
| 0 | `0 s` | `4 s` | `4 s` |
| 1 | `2 s` | `2 s` | `4 s` |
| 2 | `4 s` | `0 s` | `4 s` |

То же противоречие возникает при пересечении `Preparation → WaveActive`: первый
monster может получить движение за часть интервала, относящуюся к preparation.

Следствием становится нарушение partition invariance:

```text
advance(4)
```

может дать иное authoritative state, чем:

```text
240 × advance(1 / 60)
```

при одинаковом суммарном gameplay time и одинаковой последовательности команд.

## 3. Затронутые требования и acceptance criteria

### 3.1 Прямо затронутые FR

- `FR-005`: preparation должна длиться ровно 20 секунд и не должна входить в
  active time monsters.
- `FR-006`: scheduled spawn и скорость `1 cell/s` требуют учитывать только
  время после фактического появления каждого monster.
- `FR-010`: завышенный `routeProgress` может преждевременно привести monster к
  exit и уменьшить HP базы.
- `FR-012`: преждевременный escape косвенно изменяет отображаемые base HP,
  escaped и remaining values.

### 3.2 Прямо затронутые AC

- `AC-004`: spawn schedule формально соблюдается только по счётчику, но
  route progress созданных monsters не соответствует фактическому времени их
  присутствия в wave.
- `AC-008`: monster может быть разрешён как escaped раньше, чем пройдёт полную
  длину маршрута со скоростью `1 cell/s`.
- `AC-014`: преждевременный escape может раньше времени изменить derived
  remaining count; граница preparation должна оставаться точной.

### 3.3 Косвенное downstream-влияние

- `FR-007` / `AC-005`: завышенный progress изменяет выбор наиболее
  продвинувшейся цели и момент первого shot.
- `FR-008` / `AC-006`: неправильная позиция и active time цели изменяют
  движение и момент попадания projectile.
- `FR-009` / `AC-007`: изменённый combat timing способен изменить момент kill и
  начисления reward.
- `FR-013` / `AC-010` / `AC-011`: преждевременные escapes или kills могут
  изменить момент terminal outcome.
- `FR-016` / `AC-013`: two-tower balance fixture может дать результат, зависящий
  от размера advance steps.

## 4. Предлагаемые изменения `spec.md`

### 4.1 Уточнение `FR-005`

Добавить правило:

> Время до фактического начала волны не считается active time monsters. Если
> gameplay interval пересекает окончание preparation, wave systems применяются
> только к части interval после момента `wave-start`.

### 4.2 Уточнение `FR-006`

Добавить правила:

> Движение каждого monster начинается не ранее его scheduled spawn time. За
> рассматриваемый gameplay interval monster проходит
> `MONSTER_SPEED × activeTime`, где `activeTime` — только часть interval после
> появления monster и до его resolution.

> При одинаковой последовательности команд authoritative gameplay result не
> должен зависеть от разбиения одного и того же gameplay time на вызовы
> `advance`.

### 4.3 Уточнение `AC-004`

Добавить проверяемые условия:

- первый monster в точный момент `wave-start` имеет `routeProgress = 0`;
- monster, scheduled spawn которого совпадает с концом рассматриваемого
  interval, создаётся с `routeProgress = 0`;
- при пересечении нескольких spawn boundaries каждый monster получает только
  собственный active time;
- один крупный interval и эквивалентная последовательность меньших intervals
  дают эквивалентные session state и events.

### 4.4 Уточнение `AC-008`

Добавить условие:

> Escape может произойти только после накопления monster полной длины route за
> его фактический active time; время до scheduled spawn не участвует в escape.

## 5. Предлагаемые изменения `plan.md`

### 5.1 Key design decisions

Добавить accepted decision для обработки временных границ:

- `advance(deltaSeconds)` обрабатывает gameplay interval хронологически;
- interval разбивается по `wave-start`, spawn и последующим gameplay
  boundaries;
- сущность получает simulation updates только за время после её создания;
- итоговое authoritative state обладает partition invariance;
- events возвращаются в хронологическом порядке, а при одинаковом времени — в
  утверждённом system order и `spawnIndex` order.

### 5.2 Public runtime boundary

Уточнить контракт `advance(deltaSeconds)`:

- `deltaSeconds > 0` продвигает gameplay time на указанный interval;
- `deltaSeconds = 0` не запускает gameplay systems и только возвращает
  накопленные command-events;
- отрицательные, `NaN` и бесконечные значения отклоняются с `RangeError`;
- обработка interval не начисляет сущности время до её создания или после её
  resolution.

### 5.3 Clock и tick order

Сохранить fixed step `1/60 s` как штатный application cadence, но потребовать
корректность runtime для любого допустимого `deltaSeconds`.

Заменить недостаточно точный порядок `lifecycle → spawn → movement` на
обработку interval:

1. зафиксировать начало и конец interval;
2. определить ближайшую lifecycle, spawn или gameplay boundary;
3. продвинуть уже активные сущности только до этой boundary;
4. установить `simulationTime` в точное время boundary;
5. выполнить due transition или spawn;
6. повторять для оставшейся части interval;
7. завершить на точном `endTime` и вернуть accumulated events.

Monster, созданный на правой границе interval, не двигается до следующего
положительного interval. Тот же механизм в дальнейшем должен применяться к
tower cooldown, projectile creation/hit и terminal transitions.

## 6. Предлагаемые изменения `tasks.md`

### 6.1 `T-005`

Сохранить статус `Complete`, но расширить checks:

- `phaseStartedAt` фиксирует точную boundary независимо от размера interval;
- preparation-часть interval не передаётся wave systems;
- при завершении interval ровно на `wave-start` первый monster создаётся с
  нулевым progress.

### 6.2 `T-006`

До утверждения CR сохранить статус `Blocked`. После утверждения перевести в
`Pending`, дополнить implementation checklist и повторно реализовать:

- хронологическое разбиение interval по wave/spawn boundaries;
- движение каждого monster только за его active time;
- нулевой progress при spawn на конечной boundary;
- partition invariance;
- хронологический порядок spawn и escape events;
- отсутствие преждевременного escape.

После успешного выполнения расширенных checks перевести T-006 в `Complete`.

### 6.3 `T-007`–`T-009`

- для `T-007` распространить interval semantics на target selection и cooldown;
- для `T-008` учитывать только projectile active time после shot и сохранить
  хронологический порядок escape перед hit;
- для `T-009` прекратить обработку остатка interval сразу после terminal
  transition;
- явно сохранить dependency этих задач от исправленной и завершённой `T-006`.

### 6.4 `T-010`

Добавить проверку, что результат balance fixture одинаков при штатных fixed
steps и при другом допустимом разбиении того же gameplay time.

## 7. Влияние на завершённые задачи

### `T-001`–`T-004`

Поведенческих изменений не требуется. Toolchain, config, domain model и
building validation остаются совместимыми. Публичная сигнатура `advance` не
меняется.

### `T-005`

Основной результат задачи остаётся корректным:

- `StartGame` переводит `Ready → Preparation`;
- `phaseStartedAt` фиксируется;
- на 20-секундной boundary создаётся `wave-start`;
- повторный `StartGame` отклоняется без мутаций.

Требуется regression verification поведения при interval, пересекающем
boundary. Возможна корректировка orchestration в `GameRuntime`, но изменение
самих утверждённых результатов T-005 не требуется.

## 8. Влияние на код

Ожидаемые области изменения после утверждения CR:

- `src/game/GameRuntime.ts`: orchestration хронологической обработки interval,
  validation значения `deltaSeconds` и event accumulation;
- `src/game/lifecycle.ts`: вычисление точного времени lifecycle boundary и
  возврат неиспользованной части interval либо предоставление следующей
  boundary runtime;
- `src/game/spawning.ts`: определение scheduled spawn times и создание entities
  на точных boundaries;
- `src/game/movement.ts`: применение только active duration и разрешение escape
  в хронологическом порядке;
- будущие targeting, projectile и completion systems должны использовать тот же
  interval-processing contract.

Рекомендуется иметь один общий scheduler/boundary loop в `GameRuntime`, а не
реализовывать отдельные компенсации времени в каждой gameplay system. Это
уменьшает риск повторного расхождения timing semantics в `T-007`–`T-009`.

## 9. Влияние на тесты

### 9.1 Корректировка существующих тестов

- lifecycle test на точной границе `wave-start` должен ожидать первый monster с
  `routeProgress = 0`, а не `1 / 60`;
- существующие проверки `game-start`, countdown и повторного `StartGame`
  сохраняются;
- тесты command-events через `advance(0)` должны подтвердить отсутствие запуска
  gameplay systems.

### 9.2 Новые regression tests

Добавить сценарии:

1. interval пересекает `Preparation → WaveActive`: в движение входит только
   wave-active remainder;
2. interval пересекает одну spawn boundary: новый monster получает только
   post-spawn duration;
3. interval пересекает несколько spawn boundaries: при переходе wave time
   `0 → 4 s` progresses равны `4`, `2`, `0`;
4. coarse advance и эквивалентные fixed steps дают одинаковые snapshot и
   значимые events с допустимой floating-point tolerance;
5. monster на конечной spawn boundary не получает движение;
6. крупный interval не вызывает преждевременный escape и лишнее уменьшение
   `baseHp`;
7. invalid `deltaSeconds` отклоняется без изменения gameplay state и events.

После появления `T-007`–`T-009` добавить partition-invariance scenarios для
cooldown, projectile lifetime, hit, escape и terminal freeze.

## 10. Предлагаемый порядок миграции

1. Рассмотреть и утвердить либо отклонить CR-001.
2. При утверждении сначала обновить `spec.md`: `FR-005`, `FR-006`, `AC-004` и
   `AC-008`.
3. Обновить `plan.md`, добавив interval/boundary semantics, validation delta и
   event ordering.
4. Синхронизировать `tasks.md`: расширить T-005 checks, вернуть T-006 в
   `Pending`, дополнить T-006–T-010 timing checks.
5. Добавить regression tests для границ и partition invariance; до исправления
   они должны воспроизводить обнаруженную проблему.
6. Переработать runtime orchestration и gameplay systems в соответствии с
   утверждённым design.
7. Прогнать полный automated gate: `npm test`, `npm run lint`,
   `npm run build`.
8. Повторно проверить T-005 и выполнить все checks T-006.
9. Только после успешных checks перевести T-006 в `Complete` и разблокировать
   последовательную реализацию T-007.

До утверждения CR-001 документы `spec.md` и `plan.md` остаются source of truth,
а реализация T-006 не должна продолжаться.
